## 1. Загальне

Аудіо-контролер: інтернет-радіо + зовнішні аналогові входи, керування кнопками, енкодером та IR-пультом, кольоровий дисплей, веб-інтерфейс налаштувань.

- Збірка: VS Code + PlatformIO, Arduino framework.
- Мова коментарів у коді — українська, ідентифікатори (змінні, функції, файли) — англійська.
- Повідомлення в Serial-логах — англійською, короткі, з тегом модуля, наприклад `[IR] ...`.
- Репозиторій: https://github.com/sjorchik/esp32s3-audio-controller

## 2. ПРАВИЛА ВІДПОВІДІ (обовʼязкові)

1. Завжди видавай ПОВНИЙ текст кожного файлу, який створюється або змінюється. Ніяких фрагментів «встав сюди», «решта без змін», «...».
2. Перед кодом дай список файлів: шлях + «створено» або «змінено».
3. Не змінюй публічні інтерфейси інших модулів. Джерело правди для наявних сигнатур — ПРИКРІПЛЕНІ до цього повідомлення файли з репозиторію, а не переказ у MASTER SPEC. Якщо потрібного файлу не прикріплено, а без нього не обійтись — зупинись і запитай його. Якщо зміну зробити необхідно — явно попередь, опиши зміну і видай повні тексти всіх файлів, яких вона торкається.
4. Усі піни, таймінги, розміри буферів і прапорці — лише через `config/`, без «магічних» чисел у модулях. Існуючі `config/pins.h`, `config/features.h`, `config/defaults.h` НЕ переписуй і не дописуй у них: їх повний вміст наведено в розділі 13, використовуй ці імена точно (`pins::kBtnUp`, `defaults::kEventQueueSize`, `ENABLE_VU` тощо). Константи нового модуля клади в НОВИЙ файл `config/<module>_config.h` у тому самому стилі: `constexpr` у власному namespace (`<module>_cfg`), імена `kPascalCase`; лише прапорці умовної компіляції — `#define UPPER_CASE`. Кожен `.h` починається з `#pragma once`.
5. Не роби більше, ніж просить конкретний промпт. Модулі, які не входять у завдання, не реалізуй.
6. Використовуй лише ті версії бібліотек і тулчейн, що вказані в розділі 11. Якщо потрібна інша версія або нова залежність — попередь окремим пунктом і покажи повний фрагмент `platformio.ini` (повний файл).
7. Не використовуй блокуючі `delay()` у задачах, крім явно обґрунтованих випадків. Використовуй FreeRTOS-примітиви (черги, таймери, `vTaskDelay`).
8. Великі структури, спрайти й буфери — у PSRAM (`ps_malloc` або відповідні прапорці бібліотек), а не у внутрішній RAM.
9. IDF 5.x: використовуй ТІЛЬКИ нові драйвери — PCNT (`driver/pulse_cnt.h`), RMT (`driver/rmt_rx.h`, `driver/rmt_tx.h`), LEDC через `ledcAttach()`. Старі API (`driver/pcnt.h`, legacy RMT, `ledcSetup`/`ledcAttachPin`) не використовувати. I2S напряму не чіпати: ним володіє ESP32-audioI2S.
10. Сигнатури заглушок СВОГО модуля (розділ 12) можна змінювати, якщо цього вимагає завдання, але повідом про це окремим пунктом і видай повні `.h`. Заглушки чужих модулів не змінюй.
11. Наприкінці відповіді: розділ «Як перевірити» (що побачу в Serial / на дисплеї / у поведінці пристрою) і розділ «Відомі обмеження».
12. Якщо для завдання бракує відомостей — спочатку постав уточнювальні питання (не більше 3), а не вигадуй припущень мовчки.

## 3. Залізо

- **MCU:** ESP32-S3 N16R8 (16 МБ flash, 8 МБ octal PSRAM). Заборонені піни: GPIO 26–37 (flash/PSRAM), 19/20 (USB).
- **ЦАП:** PCM5102 (I2S). SCK підключений на GND (внутрішній PLL, MCLK не потрібен). XSMT — софт-мʼют, active-low, зовнішній pulldown 10 кОм (при старті пристрій замʼючений).
- **Аудіопроцесор:** TDA7318 АБО PT2313L (I2C, адреса 0x44, зчитування немає, автовизначення неможливе). Вибір типу зберігається в NVS, змінюється у веб-інтерфейсі. **Кількість фізичних входів різна:** TDA7318 — 4, PT2313L — 3. У проекті 4 логічних входи (WiFi Radio/TV Box/Computer/Aux); якщо обрано PT2313L, логічний вхід 3 (Aux) недоступний — UI/веб ховають пункти меню входів понад `capabilities().inputCount` (рішення зафіксовано, варіант «а» з обговорення перед Prompt 4).
- **Входи процесора:** 0 = WiFi Radio, 1 = TV Box, 2 = Computer, 3 = Aux.
- **Дисплей:** ST7789 170×320, SPI2 (FSPI, піни IOMUX), горизонтальна орієнтація 320×170. Обовʼязково врахувати зміщення вікна (offset) для панелі 170 пікселів. Підсвітка — LEDC PWM.
- **Керування:** 6 кнопок (POWER, UP, DOWN, LEFT, RIGHT, OK), енкодер з кнопкою (апаратний PCNT), IR-приймач VS1838B (RMT RX, вихід active-low).
- **IR-протокол:** RC5 / RC5X (біт toggle; у RC5X 7-й біт команди береться з інвертованого S2). Кнопки пульта навчаються користувачем (режим навчання), коди зберігаються в NVS.
- **PCM1808 (ADC):** ПІДКЛЮЧЕНИЙ до плати (рішення власника, P37 у плануванні): MCLK = GPIO16, BCLK = GPIO15 і LRCLK = GPIO17 — ТІ САМІ лінії, що й у PCM5102 (спільні), DIN = GPIO8. Аналоговий вхід АЦП знімається з виходів селектора TDA7318 (піни 17 і 7 МІКРОСХЕМИ, НЕ GPIO) — сигнал ДО регулятора гучності/тембру (підтверджено в P37). АЦП у slave-режимі (стрепи MD0 = MD1 = FMT = GND: I2S 24 біти, авто MCLK/fs), MCLK/BCLK/LRCLK дає ESP32 (I2S0, `ADC_VU_ENABLE`); канал захоплення — I2S1 RX slave. VU радіо (вхід 0) і далі рахується з декодованих PCM (до послаблення станції); VU зовнішніх входів (1–3) — з АЦП. Абстракція «джерело рівня VU» (`VuSource`) уже існує.
- **Резерв:** UART1 (TX 42, RX 48) — майбутній Bluetooth-модуль; у версії 1 не використовується.
- **Живлення:** одне джерело 12 В → 9 В (аудіопроцесор), 5 В, 3.3 В.

## 5. Програмна архітектура

**Подієва шина.** Єдина FreeRTOS-черга подій (`EventBus`). Джерела (кнопки, енкодер, IR, веб) → логічні `Action` → `AppController` → модулі. Модулі не викликають один одного напряму для керування, лише через події й `AppState`.

**Логічні Action:** див. `core/events.h` у розділі 12. Кожна подія має прапорець `repeat` (утримання) і джерело (`EventSource`).

**Розкладка керування, узгоджена з користувачем** (реалізується в `AppController`, Prompt 8):

Головний екран:
| Дія | Вхід = Radio | Інші входи |
|---|---|---|
| UP / DOWN (кнопки) | перемикання логічного входу (0..3, пропускаючи вхід 3 для PT2313L) | те саме |
| LEFT / RIGHT (кнопки) | перемикання станції | немає дії |
| OK коротко | play/pause | немає дії |
| OK утримання | список станцій | немає дії |
| Енкодер обертання | гучність (завжди, незалежно від входу) | те саме |
| Енкодер клік | цикл цілі регулювання: гучність → бас → дискант → баланс → gain → гучність … | те саме |
| Енкодер утримання | мʼют (атенюаторів, `AudioProcessor::setMute()`) | те саме |
| POWER | standby вкл/викл | те саме |

IR-пульт: OK і BACK НАВЧАЮТЬСЯ з пульта (рішення власника, P22; раніше вважалося, що на пульті цих кнопок немає); `ENC_*` не навчаються. Прямі кнопки `BASS_UP/DOWN`, `TREBLE_UP/DOWN`, `BALANCE_UP/DOWN`, `GAIN_UP/DOWN` (додані в `Action` у Prompt 7) включені в навчання (з P22 це працює; до виправлення навчання цих кнопок відповідало 409 `cannot_start`).

Меню (`Mode::Menu`) — розкладка узгоджується окремо в Prompt 9 (`ui/screens`), поки не фіксується.

**Узгоджена поведінка переходів (Prompt 8):**
- **POWER (standby):** вхід у standby зупиняє `AudioPlayer` (`stop()`), мʼютить атенюатори. Вихід зі standby відновлює той самий режим/вхід/станцію, що були до вимкнення (з `Settings.lastInput`/`lastStation`). Після ХОЛОДНОГО старту (P39: `ESP_RST_POWERON` / `ESP_RST_BROWNOUT`) пристрій стартує одразу в standby; інші перезапуски — як раніше. Якщо `lastInput` вимкнений маскою входів або недоступний апаратно — вмикається радіо (вхід 0).
- **Зміна входу (UP/DOWN):** якщо йде відтворення радіо і вхід міняється на інший — `AudioPlayer::stop()` викликається (не просто мʼют/фонова буферизація).
- **Список станцій (утримання OK):** окремий `Mode`-подібний стан, відмінний від головного екрана. Потрібен спосіб сказати майбутньому `ui/screens`, ЯКИЙ саме підрежим меню активний (список станцій — це не єдиний майбутній «підекран» у `Mode::Menu`) — конкретне рішення (нове поле в `AppStateData`, напр. enum «контекст меню», чи окремий getter у `AppController`) приймається в Prompt 8, обґрунтувати вибір.
- **Ramp гучності — ТІЛЬКИ при виході з мʼюту** (пробудження зі standby, після зміни входу/станції): AppController плавно піднімає гучність від 0 до цільового значення кроками, а потім знімає мʼют атенюаторів. Для звичайного керування енкодером/кнопками досить одного виклику `setVolume()` на подію (чіп не клацає на зміні гучності, лише на зміні входу/мʼюту) — додатковий ramp там не потрібен.
- **Мʼют атенюаторів уручну (утримання енкодера):** негайний `setMute()`, без ramp.

**AppState.** Єдине сховище стану: режим, поточний вхід, гучність, тембр, баланс, мʼют, індекс станції, метадані, статус Wi-Fi/потоку, рівні VU. Доступ потокобезпечний.

**Режими:** `Standby` (мʼют, підсвітка вимкнена, потік зупинений, Wi-Fi і веб працюють), `Radio`, `ExternalInput`, `Menu`, `IrLearn`, `WifiSetup`.

**Задачі FreeRTOS.** Аудіо — окреме ядро від UI і мережі. UI малює зі спрайту (double buffering у PSRAM), без блокувань аудіо. Ядра й пріоритети задач — константи в config.

**Ядра й пріоритети задач (фіксовано):**
- Ядро 0: введення (кнопки, енкодер, IR), AppController, UI/дисплей, Wi-Fi, веб-сервер.
- Ядро 1: аудіо (ESP32-audioI2S, декодування, I2S). На ядрі 1, крім аудіозадачі, нічого не запускати; Arduino `loopTask` там теж є (ядро 1, пріоритет 1) — до появи AppController це не заважає аудіо (нижчий пріоритет, задача майже завжди спить), але після AppController `loop()` лишається порожнім і нічого туди не додається.
- **Зайняті пріоритети (ядро 0):** введення (кнопки, енкодер) = 4 (`input_cfg::kBtnTaskPriority` / `kEncTaskPriority`).
- **Зарезервовано:** аудіо (ядро 1) — довільне число, ВИЩЕ за 4 (визначається у Prompt аудіо, не звірене з ядром 0). AppController — нижче за 4, вище за UI (орієнтовно 3). UI/дисплей — нижче за AppController (орієнтовно 2). Мережа/веб — найнижчий (орієнтовно 1).
- Кожен наступний модуль порівнює своє число з цією таблицею й одразу після реалізації оновлює її фактичним значенням.
- Кожна задача періодично віддає процесор (vTaskDelay / блокуюче очікування черги); задачі не мають годувати watchdog вручну.

**Збереження.** Налаштування — NVS (namespace `audioctl`). Станції, шрифти, іконки, веб-сторінки — LittleFS.

**Флеш 16 МБ.** Таблиця розділів (P24b, `partitions.csv`): `nvs` 0x9000 + 0x5000, `otadata` 0xE000 + 0x2000, (вільно 0x10000–0x1FFFF), `app0` 0x20000 + 0x580000, `app1` 0x5A0000 + 0x580000, `spiffs` (LittleFS) 0xB20000 + 0x4E0000; кінець 0x1000000. Збірка PlatformIO/pioarduino пише `boot_app0.bin` за ФІКСОВАНОЮ адресою 0xE000 незалежно від `partitions.csv` (підтверджено логом esptool: bootloader 0x0, partitions 0x8000, boot_app0 0xE000, firmware 0x20000), тому `otadata` ОБОВʼЯЗКОВО має покривати 0xE000..0xFFFF; не переміщувати без перевірки логу `pio run -t upload -v`. Процедури прошивки, міграції й відновлення — `docs/flashing.md`. Board: `esp32-s3-devkitc-1`, `board_build.arduino.memory_type = qio_opi`, консоль на UART0.

## 7. Інтерфейс аудіопроцесора

Спільний абстрактний інтерфейс для TDA7318 і PT2313L (актуальний код — розділ 12):

- `begin()`, `setInput(index)`, `setVolume(value)`, `setBass(value)`, `setTreble(value)`, `setBalance(value)`, `setGain(value)` (Prompt 7: підсилення ПОТОЧНОГО входу, сирі апаратні кроки `gainMin..gainMax` — для обох чипів 0..3; TDA7318 крок 6.25 дБ, PT2313L крок 3.75 дБ, значення для решти входів тримає сам драйвер у приватному `m_gain[]`), `setMute(bool)`, `setLoudness(bool)`, `probe()` (ACK на I2C-адресу, стан не змінює), `applyAll()` (повторно надіслати весь закешований стан — спершу мʼют гучномовців окремою транзакцією, потім решта, потім повернути баланс), `i2cErrorCount()`, `cachedState()` (тепер містить і `gain` активного входу).
- `capabilities()` — реальні можливості чипа: `bass`, `treble`, `balance`, `loudness`, `inputCount` (TDA7318 = 4, PT2313L = 3 — див. розділ 3), `volumeMin/Max`, `toneMin/Max`, `balanceMin/Max` (усе — шкала UI, не сирі регістри), `fader` (апаратно є в обох чипах, але інтерфейс не дає `setFader()`, тому завжди `false`), `inputGain` (булевий прапорець, в обох драйверів `true`), `gainMin/Max` (Prompt 7: сирі кроки, завжди 0..3 для обох чипів).
- UI/AppController ховають непідтримувані функції та пункти входів понад `inputCount`.
- Плавна зміна гучності (ramp) — відповідальність ВИКЛИКАЧА (`AppController`): він сам покроково викликає `setVolume()`; драйвер не блокує і не має власного таймера. Кожен виклик — одна коротка I2C-транзакція; повторні однакові значення в шину не йдуть (кеш `audio_i2c::RegShadow`).
- Мʼют = мʼют усіх атенюаторів гучномовців (регістр гучності не чіпається). Послідовність «мʼют → зміна входу/станції → розмʼют» координує `AppController`; драйвер надає лише окремі примітиви.
- Спільна I2C-шина (`audio/audio_i2c`): один статичний рекурсивний мʼютекс на обидва драйвери й на тестовий режим, кеш підтверджених байтів на регістр, таймаут і повтори транзакцій — константи в `config/audio_config.h`.
- Рівні I2C: підтяжки до 3.3 В, швидкість 100 кГц; при живленні процесора 9 В пороги логічної одиниці звірені за даташитом (винесено в реалізацію драйверів).

## 8. Wi-Fi provisioning

- Немає збереженої мережі або 3 невдалих спроби підключення → режим AP з назвою `AudioCtrl-Setup`, captive portal (DNS), сторінка: скан мереж, вибір, пароль → збереження в NVS → перезапуск у режим STA.
- На дисплеї в цей час — інструкція (назва AP, адреса).
- Скидання Wi-Fi — утримання кнопки OK під час старту.
- (P28) Поки піднята AP (на БУДЬ-ЯКОМУ вході) — `Mode::WifiSetup`: екран налаштування «Setup Wi-Fi» з підказкою «OK: work offline», звук замʼючено, реагують лише POWER (standby; утримання ≥ 3 с = перезапуск) і коротке OK / клік енкодера. OK = офлайн-режим: Wi-Fi вимкнено (`WiFi.mode(WIFI_OFF)`, AP / портал / веб-сервер / mDNS зупинені), усі входи, крім радіо; режим не зберігається в NVS, вихід — перезапуск (утримання POWER або живлення). До підняття AP (спроби STA ≈ 10–30 с після старту) вибраний вхід працює як звичайно.
- (P29) Список до 5 збережених мереж (SSID + пароль, порядок = пріоритет; NVS namespace `wifinets`, ключ `list`, один блоб із версією). Старт і втрата звʼязку: раунд = скан (якщо мереж ≥ 2) → видимі збережені за пріоритетом (інакше усі напряму) → спроби по черзі; після старту 3 невдалих раунди або бюджет 60 с → AP; під час роботи раунди повторюються без AP; підключений пристрій на мережу вищого пріоритету сам не перемикається. Портал AP додає мережу на ПЕРШЕ місце, решту не стирає (повний список → випадає остання). Стара одинична мережа з `esp_wifi` переноситься в список автоматично. Скидання Wi-Fi (API або утримання OK при старті) стирає ВСІ мережі й піднімає AP.
- Та сама веб-частина, що й для налаштувань: після підключення до мережі доступний повний інтерфейс за адресою mDNS (`audio.local`) і IP.

**Архітектурні рішення й інваріанти (дотримуватись у нових промптах):**
1. Веб-команди керування виконує `AppController::runWebCommand()` (абсолютні значення, результат із `reason`), НЕ `EventBus`; з HTTP-хендлерів не чіпати залізо напряму (виняток — read-only геттери). Хендлери виконуються в задачі AsyncTCP: не блокувати; довгі й мережеві дії — через прапорці / задачі (шаблон «прапорець + задача wifi», відкладений `api_restart`).
2. Веб-сторінки ВБУДОВАНІ в прошивку як gzip-масиви (`webui/` → `tools/build_web.py` через `extra_scripts = pre:` → `src/net/web_assets_gen.cpp`, у `.gitignore`); LittleFS зберігає лише `stations.json` (не використовувати `uploadfs` — стирає станції). Нові сторінки додаються ЛИШЕ в `webui/` без правок C++. Конвенції фронтенду — `docs/web_ui.md`: спільне ядро `common.js` (послідовна черга `api.*`, `CONFIG`, `REASONS`, `createPoller`, `waitForDevice`, …), `app.css`, `nav.js`; все від пристрою вставляти тільки через `textContent`.
3. Індекс станції ПОЗИЦІЙНИЙ (стабільного id немає); `AppController` не відстежує, яка станція реально грає після `move` / `remove`; сторінки перечитують список після кожної зміни.
4. Звук ПО ВХОДАХ (P21b): гучність, бас, дискант, баланс, gain, loudness зберігаються в профілі кожного входу (NVS `audioctl`, blob v2); профіль застосовується ПІД мʼютом при зміні входу, виході зі standby й на старті; мʼют користувача глобальний. Усі зміни звуку проходять через одне місце в `AppController` (`persist()` → `captureActiveProfile()`).
5. Рівень станції (P25): `Station::levelDb` (−24…0 дБ, за замовчуванням −20, константи в `config/station_level_config.h`); послаблення — власне множення семплів у хуку `audio_process_i2s` (`audio/output_trim.*`), застосовується ДО початку звуку при запуску станції й наживо при редагуванні поточної; VU рахується ПІСЛЯ еквалайзера, але ДО послаблення станції (P34: порядок у хуку `eq::process` → вимір VU → `output_trim::process` → I2S, щоб рівень станції −20 дБ не стискав шкалу VU); `audio/vu_pcm_hook.cpp` НЕ підключає `Audio.h`; `VU_PCM_HOOK_STYLE != 1` вимикає і VU, і рівні станцій.
6. Підсилювач STBY (P23c): `pins::kAmpStby` = GPIO46 (1 = працює, 0 = standby; strapping-пін, внутрішній pull-down при скиданні); вмикання — пін HIGH під мʼютом, прогрів `kAmpWakeMs`, потім розмʼют; вимкнення — мʼют, через `kAmpOffDelayMs` LOW; `FEATURE_AMP_STANDBY`.
7. Розкладка flash (P24b): збірка пише `boot_app0.bin` за ФІКСОВАНОЮ адресою 0xE000, тому `otadata` обовʼязково на 0xE000 (`nvs` 0x9000 + 0x5000); `app0` / `app1` / `spiffs` не переміщувати; імʼя розділу LittleFS лишається `spiffs` (попередження `gen_esp32part.py` безпечне). Процедури — `docs/flashing.md`.
8. IR (P22): `kActionCount` = `GAIN_DOWN + 1` (дії BASS_* … GAIN_* у таблиці IR; порядок enum безперервний, `static_assert`); OK і BACK навчаються, `ENC_*` ні; формат NVS мапи не змінювався.
9. Режими мережі (P28, P29): поки піднята AP — `Mode::WifiSetup` на будь-якому вході (звук замʼючено, реагують лише POWER і коротке OK / клік енкодера); OK = офлайн (Wi-Fi вимкнено, усі входи крім радіо; не зберігається, вихід — перезапуск); утримання POWER ≥ `input_cfg::kPowerRestartHoldMs` (3 с) = «тихий» перезапуск (мʼют → амп LOW → `ESP.restart()`) у всіх режимах. Список мереж Wi-Fi — NVS `wifinets` (до 5, порядок = пріоритет, паролі не повертаються API); на мережу вищого пріоритету сам не перемикається; портал AP додає мережу першою.
10. Мова: написи на ДИСПЛЕЇ — англійською (Volume, Playing, Bass, Treble, …); веб-інтерфейс і документація — українською («тембр НЧ» / «тембр ВЧ», «Вхід 1…4» у навчанні пульта).
11. Еквалайзер (P30): 5 смуг (`eq_cfg::kBandFreqHz`), peaking RBJ biquad (DF2T, float, Q=1.0), діє ЛИШЕ на радіо — архітектурно, бо хук `audio_process_i2s` викликається лише для декодованого потоку ESP32-audioI2S; зовнішні входи йдуть аналоговим трактом і хук не минають. Порядок у хуку (P34): `eq::process` → вимір VU → `output_trim::process`. Один ГЛОБАЛЬНИЙ пресет (`Settings::eqGainsDb[5]`, НЕ по входах і НЕ по станціях), NVS blob v3 (міграція v1/v2→v3, `eqGainsDb` = 0 за відсутності). Коефіцієнти перераховуються при зміні пресету чи частоти дискретизації потоку (атомарний лічильник версії); частота береться з `AudioPlayer`/ESP32-audioI2S (`#if EQ_SAMPLE_RATE_FROM_LIB`, НЕ перевірено на залізі).

**Відкритий беклог (стисло; деталі — `docs/history.md`):**
- *Перевірити на залізі (P30, за потреби):* поведінка на різних частотах дискретизації потоку; навантаження CPU ядра 1 при 5 активних смугах; клацання при зміні пресету наживо; 12 кГц смуга вимкнена при fs < 26.7 кГц.
- *Документація / коментарі:* застарілі місця, знайдені в P41, закрито в P41–P42 (лишень `gen_digits_font.py`: default `--em` = 80, реально потрібно 112 — приклад команди в докстрінгу виправлено, default не змінювався).
- *Веб (P30b):* пресет еквалайзера не опитується (зміна з іншого клієнта видна після зміни входу / перезавантаження сторінки); мобільну розкладку секції не перевірено окремо.
- *Перевірити на залізі:* чи `WiFi.begin()` не пише flash при кожній спробі (розглянути `WiFi.persistent(false)` після міграції); кириличні паролі (байти чи символи).
- *Безпека:* автентифікації веб-API немає (reboot / factory-reset / OTA / список Wi-Fi доступні будь-кому в мережі); паролі Wi-Fi в NVS у відкритому вигляді; WPA2-Enterprise не підтримується. OTA без автовідкату (потрібен bootloader з rollback — суттєва зміна збірки).
- *Прошивка:* «тихий» перезапуск для веб `reboot` / `factory-reset` / успішного OTA (зараз без мʼюту — можливе клацання); `publishState()` бере `SettingsStore::snapshot()` під `s_lock` (кандидат: кешувати назви входів); версія прошивки — ручна константа `web_api_cfg::kFirmwareVersion`, `buildDate` ненадійна; `/api/system` важкий (`LittleFS.usedBytes()`); тембр у standby; профілі неактивних входів можна редагувати лише перемикаючи вхід.
- *Контракт API:* імпорт станцій лише «замінити» без підсумку; CRUD станцій не документує 409 під час OTA / IrLearn; `cannot_start` в IR неоднозначний; `/api/ir/actions` без `rc5x`; немає нейтральних значень тембру в API; `502` від `/api/settings` без коду.
- *Веб:* `home.js` → перехід на `createSlider`; кілька сторінок перевищили орієнтири обсягу; перевірити на вузьких екранах і мобільних браузерах (iOS Safari: XHR-прогрес OTA).
- *Залізо:* тріск «в такт музиці» при мʼюті / малій гучності й потріскування ≈ раз на секунду при відкритому веб-інтерфейсі — ВИРІШЕНО (апаратна причина, усунено власником; програмних змін не було). PCM5102 дає ≈ 2.1 Vrms при 0 dBFS — рівень регулюється `levelDb` станції. Пін XSMT (GPIO45, pulldown 10 кОм) краще тримати під керуванням прошивки: підключення до +3.3 В прибирає захист від клацань при завантаженні, зміні станції, standby, OTA; при жорсткому підключенні GPIO45 слід від'єднати від лінії.

## 14. Веб-API (огляд; повний контракт — `docs/web_api.md`)

Джерело правди — `docs/web_api.md` у репозиторії (прикріплювати до кожного веб-промпту; цей розділ — лише огляд).

| Група | Ендпоїнти |
|---|---|
| Стан | `GET /api/status` (розширений P18), `/api/settings` (P13) |
| Входи (P39) | `GET /api/inputs` → `{"inputs":[{index,name,available,enabled,selectable,canDisable}×4],"enabledMask":N,"input":N}`; `POST /api/inputs` `{"enabled":[true|false|null ×4]}` або `{"index":N,"enabled":bool}` → 200 `{"ok":true,…як GET}`; 400 `no_body`/`invalid_json`/`unknown_field`/`missing_field`/`conflicting_fields`/`invalid_value`/`out_of_range` (index 0..3), 409 `ota_in_progress`/`ir_learn_active`, 413, 503 `busy`; вхід 0 мовчки ігнорується (завжди enabled); дозволено в standby. `GET /api/status.inputs[]` (`index`,`name`,`available`) НЕ змінено (без `enabled`). Повний контракт — `docs/web_api.md` §12 |
| Керування | `POST /api/power` · `/api/mute` · `/api/volume` (value \| step) · `/api/gain` · `/api/input` (409 `input_disabled` для вимкненого входу) · `/api/player/{play,pause,stop,toggle,next,prev}` · `/api/player/station` |
| Станції | `/api/stations*` (P14): список, add/update/remove/move, імпорт JSON/M3U/PLS, експорт; P25: поле `levelDb` (−24..0, за замовчуванням −20) |
| IR | `/api/ir*` (P15): навчання, мапа, імпорт/експорт |
| Wi-Fi | `GET /api/wifi`, `GET` / `POST /api/wifi/scan`, `POST /api/wifi/networks`, `POST /api/wifi/networks/move`, `DELETE /api/wifi/networks/{index}`, `POST /api/wifi/connect`, `POST /api/wifi/reset` (`confirm:true`, стирає ВСІ збережені мережі) (P29) |
| Система | `GET /api/system`, `POST /api/system/reboot`, `POST /api/system/factory-reset` (`confirm:true`), `/api/ota` (P16) |
| Еквалайзер | `GET`/`POST /api/eq` (P30): 5 смуг, `gainsDb[5]` або `band`+`gainDb`, −12..+12 дБ; лише радіо (архітектурно, без прапорця входу) |

**Угоди:**
- Усі команди керування виконує `AppController::runWebCommand()`; з HTTP-хендлерів не чіпати залізо напряму (виняток — read-only геттери).
- Помилки — єдиний JSON-формат; для відмов керування є поле `reason` (коди в розділі 11, P18).
- Індекс станції позиційний, стабільного id немає.
- Хендлери виконуються в задачі AsyncTCP: не блокувати; reboot/factory-reset відкладені одноразовою задачею `api_restart` (ядро 0, пріоритет 1, стек 4096, ~1.5 с до `ESP.restart()`), відповідь клієнту йде ДО перезапуску.
- Тіло JSON ≤ 1024 Б.
- `WEB_API_DEV_CORS` (за замовчуванням 0): CORS-заголовки для розробки сторінок на ПК без перепрошивки.
- Статичні сторінки віддаються явними GET-маршрутами (`registerStaticRoutes`) з масивів у flash; `onNotFound` не змінювався (його може використовувати captive portal).
- `station.name` у `GET /api/status` — назва станції зі списку для `station.index` (запасно ICY-назва, потім порожній рядок); `station.icyName` відсутній (P20b).
- Звукові параметри (`/api/volume`, `/api/gain`, `/api/settings` bass / treble / balance / loudness, `/api/status`) стосуються профілю ПОТОЧНОГО входу; gain зберігається (P21b). Нових ендпоїнтів немає.
- IR-навчання: `POST /api/ir/learn` → `GET /api/ir/learn/status` (`Waiting`, `Confirm`, `Conflict`, `Success`, `Timeout`, `Idle`), далі `confirm-overwrite` / `cancel`; таймаути пристрою 8 с / 15 с (`ir_cfg::kLearnTimeoutMs`, `kLearnConflictTimeoutMs`) в API не віддаються.
- `waitForDevice` (фронтенд) опитує `GET /api/status` після перезапуску; `POST /api/system/reboot` шлеться без тіла. Для `wifi/reset` відповіді не чекають (пристрій змінює мережу).
- Wi-Fi (P29): індекси мереж позиційні; паролі API ніколи не повертає; мутуючі маршрути й скан відповідають 409 `ota_in_progress` / `ir_learn_active`, 503 `busy` під час перезапуску; `connect` відповідає ДО перемикання, зʼєднання клієнта після цього обривається, IP може змінитись.
